This post documents the Unreal Engine 5.8 plugin stack I use for R&D prototyping and, more importantly, the criteria behind every entry. Each system was integrated one at a time into a dedicated Sandbox project, validated in Play-In-Editor and in a packaged Windows build, and backed up before the next one went in. The goal is not to collect plugins: it is to shorten the path from an ambiguous requirement to a testable prototype, and to spend custom engineering time only where it creates real value. The last section covers what AI coding agents change in these decisions.

The decision rule applied before any system enters the stack:

  • Unreal native first: if the engine solves the problem well enough, no plugin is added
  • Mature existing plugin second: maintained, documented, version-current, used in real projects
  • Integrate or extend third: adapters and diagnostics go into BertaDevKit, never forks of commercial code
  • Custom development last, only when requirements, ownership, performance or reuse justify it
  • A discount times a purchase; it never justifies one. A plugin needs a concrete experiment or a recurring problem

The interaction, narrative and items layer covers how the player acts on the world and how story progresses:

  • Nice Interaction System V2 for generic player-to-world interaction (doors, pickups, contextual actions), attached to the existing PlayerController and GameState rather than replacing them
  • Inspection System Pro for examining objects, documents and discoveries: a different problem from generic interaction
  • Narrative Tales for dialogue, branching and quests; interactables react to player choices through the Dialogue Option Selected delegate
  • Inventory System Pro for items, equipment and containers, only when a prototype actually needs ownership of items
  • Menu System Pro as the CommonUI and Enhanced Input foundation for menus, settings and basic save support
  • Map System Pro and Objective Path Guide for map-based navigation and temporary in-world route guidance, enabled only when the design needs them

The camera layer separates gameplay cameras from cinematic presentation:

  • Ultimate Gameplay Camera as the default gameplay camera: data-driven presets (near / medium / far as Camera Data Assets), dynamic spring arm with predictive collision, and Camera Focus driving a GAS-based target lock
  • Black Eye Camera kept for projects whose presentation model fits it, not enabled by default
  • Native Sequencer for authored cinematic timing, rather than forcing it into runtime camera logic

The atmosphere and visual presentation layer is split by what each tool changes:

  • Ultra Dynamic Sky changes the environment: sky, time of day, clouds, weather and fog, with looks stored as native configuration assets instead of custom presets
  • Screen Space Fog Scattering adds light scattering on top of the existing height fog; a lightweight complement, not a weather system
  • Chameleon Post Process changes how the player perceives the scene: memories, visions, damage states, stylization. Its value is lower in forward-rendering and VR setups because many effects rely on deferred buffers
  • Fluid Ninja VFX Tools for simulated and baked fluid effects ahead of runtime

The gameplay and character layer is enabled only when the mechanics call for it:

  • GAS Companion to accelerate Gameplay Ability System setup: abilities, stamina costs and regeneration through Gameplay Effects, and the built-in attribute HUD
  • Combo Graph for combo-driven combat, and Ninja Input only when input orchestration becomes complex enough to justify another layer over Enhanced Input
  • State Tree Tools on top of native StateTree, which remains the baseline for state-driven behaviour
  • Dragon IK for procedural IK when it measurably shortens implementation compared with native IK Rig and Control Rig
  • PCGEx to extend native PCG graphs, and Runtime Audio Importer for runtime audio and voice experiments

The diagnostics, AI and editor productivity layer keeps iteration fast and observable:

  • BertaDevKit, my own open-source toolkit, holds reusable diagnostics, audits and optional integrations with third-party systems (for example console dumps and editor audits for camera setups, and a shared Gameplay Tag catalog)
  • Advanced Game Logging for logging in packaged builds, outside the editor
  • Blueprint Assist, Electronic Nodes, Auto Size Comments, Global Search Pro and LE Extended Standard Library for faster, more readable Blueprint work and navigation

The overlaps in the stack are resolved by responsibility, not by picking a winner:

  • Ultra Dynamic Sky changes the physical atmosphere; Chameleon changes perception. Combined, they produce narrative mood transitions
  • Nice Interaction handles acting on objects, Inspection handles discovering them, Inventory handles owning them
  • Dragon IK and native IK genuinely overlap: the cheaper native option is the default, Dragon IK is used when it saves time
  • StateTree versus Logic Driver Pro is still open and will be measured on a real cross-plugin orchestration flow

The integration lessons are where most of the value of this exercise came from:

  • One system at a time: integrate, test in PIE, package, back up. Installed and enabled does not mean validated
  • Ultimate Gameplay Camera preset cycling only worked reliably after creating a child camera manager with its own Default Camera Data, set to one of the presets in the cycle
  • A native SpringArmComponent left next to the UGC spring arm made the camera hug the character and hid the preset differences; removing the old boom fixed it
  • UGC Camera Focus refuses to start while yaw or pitch follow is active, and pitch follow is enabled by three separate flags; disabling only one is not enough
  • In GAS, an Activation Blocked Tag driven by CharacterMovement state (InAir) is a cleaner fix for mid-air re-activation than extra checks inside the ability
  • Plugins that need their own PlayerController or GameState components integrate better into the existing classes than into new ones created per plugin

The plugins I did not buy say as much about the criteria as the ones I did:

  • Easy Multi Save: native SaveGame and Menu System Pro cover the persistence small prototypes need; it becomes relevant with real world-state complexity
  • Blockout Tools: prototypes start from existing levels, PCG or empty maps, so greyboxing is rarely the bottleneck
  • MeshBlend and MeshPack: strong tools for environment art and very large inherited scenes, neither of which is a current need
  • Fluid Ninja LIVE and Shader World: genuinely new capabilities, but expensive and with a learning cost; they wait for a prototype that needs interactive fluids or GPU terrain beyond PCG
  • VR Hands Procedural Grab and Steam integration: no active XR or Steam-bound project, so buying now would be speculative
  • Logic Driver Pro is the strongest remaining candidate because it would add an orchestration layer across existing systems rather than duplicate one of them

The impact of AI coding agents on these decisions is a working hypothesis, to be measured in upcoming posts on UE 5.8 with its official MCP plugin:

  • Wrappers and glue (simple save systems, platform wrappers, localization automation) are now much cheaper to build on demand, so they are harder to justify buying
  • Deep, battle-tested technology (camera systems, sky and weather, fluids, terrain) keeps its value: what you pay for is years of edge cases
  • A new criterion appears: how well an agent can work with the plugin. Plain C++ APIs, data assets and console commands are agent-friendly; custom graph types are only friendly if the vendor exposes them, as Logic Driver now does with its experimental MCP companion, Logic Driver Assist
  • Diagnostics matter more than before: an agent that can run an audit and read a structured result can verify its own changes instead of just reporting success
